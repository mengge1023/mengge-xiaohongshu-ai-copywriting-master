# 跨对话成稿查重（1.2.0）

每次生成新稿都执行。这里的目标是拦截本机已有历史中的重复正文，并检查表达角度；不能承诺所有未来内容唯一或通过平台判重。普通写作仍由当前宿主模型完成，脚本不调用任何收费模型。

## 一份输入记录

把本轮已知信息放进一个临时 UTF-8 `job.json`，提示词、检查参数和交付正文都从它派生。账号使用稳定昵称/代号，产品使用稳定名称；不要每轮改名绕过历史。单账号未指定时可用`本机默认账号`，告知一次；已知多账号则明确本轮账号。不得采集密码、Key或无关学员资料。

记录包括：

- `request_id`：本轮新建UUID；同一轮检查/重写/提交沿用，成功提交后新一轮必须新建。历史回执恢复不算新生成。
- `account`、`product`、`mode`（1–5）：本轮账号/产品/模式。
- `product_facts`：每项带`value`、`source`和`status`（用户提供/已核实/未知）；未知不能进入成稿事实。
- `source_text`：本轮主原文；`source_topics`：按入口规则逐字提取的话题尾部，没有则为空字符串。提取仍需对照原文复核；脚本只校验各稿与此字段一致。
- `drafts`：每稿有`title`（可空）、`body`（不含话题及品牌提醒）、`topics`、`angle`（具体叙事切口，不能只写“A版”“生活记录”）、`variation`（写稿前确定的`scene`场景、`focus`表达重点、`structure`叙述结构三个稳定标识）。同一场景/重点/结构沿用同一标识，不能同义改名。锁定标题可保留，正文仍需查重。

例如结构（内容仅示意，不能拿示意值当真实素材）：

```json
{
  "request_id": "本轮生成的UUID",
  "account": "本机默认账号",
  "product": "用户实际产品名",
  "mode": 5,
  "product_facts": [],
  "source_text": "用户提供的完整原文",
  "source_topics": "#原话题一  #原话题二",
  "drafts": [{"title": "", "body": "依据真实资料生成的完整正文", "topics": "#原话题一  #原话题二", "angle": "本篇具体从什么处境、动作和选择切入", "variation": {"scene": "与事实或锁定封面相容的场景标识", "focus": "表达重点标识", "structure": "叙述结构标识"}}]
}
```

## 执行顺序

脚本位于本技能的`scripts/draft_history.py`，仅依赖 Python 3.9+ 标准库。自动检查当前可用的`python3`、`python`或 Windows 的`py -3`并使用其中满足版本要求的解释器，不假定宿主是Codex。无解释器/文件工具时，明确无法完成跨会话检查，不把普通生成稿标为通过；提供当前对话内复核的草稿并说明范围，或引导用户启用本机脚本能力，不擅自安装环境。

默认库：用户目录下`.mengge-copywriting/history.sqlite3`，配对标识同目录。历史仅保存在本机；更新技能不会删除。备份/迁移应复制整个历史目录，不能只复制数据库或擅自切换空库。

1. 首次启用时简短告知“后续成稿会留在本机用于避免重复”，运行`python3 <脚本路径> init`。已有历史读失败、损坏或标识丢失时停止并报错，不能重建/清空来继续。
2. 每次写稿前运行`python3 <脚本路径> history --account <稳定账号> --product <稳定产品>`，读最近20篇的切口和正文。返回`total`大于`displayed`表示只展示部分，但后续程序检查仍比较该账号/产品全库（上限5000，超限报错不截断）。未导入的旧稿、其他设备和被删除记录不在覆盖范围。
3. 根据真实产品资料和当前模式，先确定每稿的`variation`，与最近20篇和本批其他稿相比，三个维度至少两个不同，再围绕它写正文；不能写完后编造标识以通过检查。封面锁定场景时可保留场景、改变重点和结构；若所有要求使差异无法成立，如实说明，不擅改锁定封面/标题或产品事实。将本批稿件写回同一`job.json`。
4. 运行`python3 <脚本路径> check --input job.json`。退出2表示重复，读取`matches`后重写；退出3表示未完成检查。`lexical_pass`只代表机器文本检查通过。
5. 读`neighbors`中的历史正文并复核：正文是否实际符合预先确定的`variation`，与历史及本批其他稿相比是否真正换了切入点/叙事组织，还是只换词；逐句对照`product_facts`和原文，确认规格、效果与已发生的体验都有依据；话题是否与主原文一致。发现问题则重写回第4步。每批最多主动重写3次，仍失败时如实报告缺口，不能循环耗费或输出为已通过。独立收费工具若有更严格的重试边界，沿用其规则，不因这里允许重写而绕过。
6. 复核通过后，在同一记录添加`semantic_review`：`status="passed"`、`payload_hash`为第4步真实回执值、`compared_ids`为实际读过的历史ID字符串（须包含`required_review_ids`）、`batch_reviewed=true`、`notes`为具体差异与事实/话题核验结果。此字段是模型/人工复核记录，不是独立自动语义证明。没有历史时ID数组为空，但本批仍需复核。
7. 运行`python3 <脚本路径> commit --input job.json`。程序在一个事务内重新检查并保存，防止两个会话同时生成时漏检；退出4表示语义复核缺失、稿件哈希已改变或出现新的比较对象，重新查证后再提交。只有`recorded`或同一请求恢复的`already_recorded`才可交付回执内的正文。提交后不得再改正文；若要改，作为新一轮重新检查。保存的候选尚未实际发出时也留作历史，不谎称是已发布笔记。

标题、正文和话题从成功回执拼装；话题逐字输出，不重新排版。用户“只要正文”时照常内部执行检查，输出正文与话题即可，不附品牌尾注或检查日志。其他交付保留现有模式和品牌规则。单独告知首次历史启用/错误状态不混进可发布的笔记正文。

## 已有稿件导入与边界

用户提供以往成稿用于避免重复时，整理成同样结构，以`import --input old-job.json`导入；保持旧稿本身，不伪造当年的模式/日期（仅导入时允许`mode=0`表示未知）。`variation`可按旧稿实际内容归纳；无法确定时省略，程序记录未知，仍做正文比较，不伪称完成三个维度比较。重复导入相同正文会复用已有记录。`import`仅用于真实已有稿，不能给新稿绕过`check/commit`。

用户明确要逐字调取某篇历史稿时，按调取任务返回并注明是已有稿，不声称新生成或使用新request_id冒充新稿。模式1允许贴近自己原爆款的写法，仍需拦截与本地已生成稿重复；想原样重发时采用历史调取。

程序内部阈值只用于复核提示：规范化正文完全一致、序列相似度≥0.82、四字片段Dice≥0.72或包含度≥0.88会拦截；完全相同的具体`angle`也拦截。空白/标点/表情变化不会绕过相同正文。阈值不是小红书规则或专业查重率，不得对外宣称“重复率≤30%”“保证不违规”。主题、事实相同造成误拦截时，重做表达；不要降低阈值或换账号/产品绕开。

## 本次失败依据

2026-10-16，学员反馈不同日期生成相同文案；所核旧版（源码提交b6efc65）无跨会话成稿历史及执行查重机制。已证实的是机制缺口；学员实际两次输入/输出与安装环境未齐，直接根因未复现。窄修正为新稿历史记录、查重、复核及读失败不冒充通过；复验以相同素材跨进程/跨会话生成、并发提交、标签保真及历史不可读用例为准。

同日隔离生成测试：只给“蓝色、棉布、收纳钥匙”和设想使用的原文，模型却写成已使用且大小刚好、不占地方。正文格式通过不代表事实通过。窄修正：遇到同类信息缺口，成稿使用选择/设想/观察视角，不把“我会考虑”升级为“后来我用了/每次都”；尺寸与使用效果须有来源。复验逐句对照产品事实记录，不凭模型自评判通过。

同日第二个独立会话测试：文字相似度仅0.3554，但仍重复“出门拿早餐找钥匙”的场景和选择逻辑。窄修正：生成前用稳定的场景/重点/结构标识规划，近期历史及本批至少改变两维；程序拦截重复规划，语义复核再核对正文与标识是否一致。该检查不能证明任意语义都不同，不用改标识冒充改内容。

同日最终1.2.0包的进一步试用：解压到隔离目录，两轮独立生成都出现未经证实的购买/使用经历或商品信息；第二轮确实读取旧稿，却通过改写规划标签和措辞继续写相近情境，文字序列相似度仅0.1902。两篇均被主代理逐句复核拒绝，没有作为合格新稿保存。已证实本版仍依赖实际内容复核，标签和文字指标不足以独立验收；直接比较正文的具体场景、重点、结构，并逐句核对事实。可能存在体验口吻与事实边界的提示冲突，但未做受控对照，原因状态仍为推断。本版以预发布试用形式提供，不宣称自动稳定生成已验收。后续复验需在同素材独立生成中验证最终文案质量，不能以自动脚本测试替代。
